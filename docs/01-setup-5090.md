# Setup — RTX 5090

The 5090 is Blackwell (`sm_120`). It will not run on an older CUDA stack, and the failure is
cryptic, so deal with this first.

## 1. Confirm the card and driver

```bash
nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv
```

Expect ~32768 MiB. Driver should be 570+.

## 2. The Blackwell trap

If you reuse an old ComfyUI install you will hit:

```
CUDA error: no kernel image is available for execution on the device
```

That means PyTorch was compiled before your GPU existed. It is not a VRAM problem and no setting
fixes it. You need:

- **CUDA 12.8 or newer**
- **PyTorch 2.7+ built for cu128**

Verify after install:

```bash
python -c "import torch; print(torch.__version__, torch.version.cuda); print(torch.cuda.get_device_name(0)); print(torch.cuda.get_device_capability(0))"
```

You want capability `(12, 0)` and a `cu128`-tagged torch build. Anything else and stop here.

## 3. Install ComfyUI

**Install ComfyUI Desktop fresh.** Do not reuse an old portable folder — it ships pinned wheels
from before Blackwell and that is the single most common way this goes wrong.

<https://www.comfy.org/download>

## 4. Get the Wan 2.2 FLF2V workflow

Do not hand-assemble the graph or hunt for weights manually. ComfyUI ships official templates
that pull the correct files for you:

1. Open ComfyUI
2. **Workflow -> Browse Templates -> Video**
3. Pick the **Wan 2.2 First-Last-Frame to Video (FLF2V)** template
4. Accept the model downloads when prompted

That fetches the diffusion model, the UMT5 text encoder and the Wan VAE into the right folders.
Expect roughly 20-40 GB depending on which variant you take.

## 5. Pick the model size

| Variant | VRAM | Notes |
|---|---|---|
| 5B TI2V | ~8-16 GB | Fallback. Use on smaller cards. |
| **14B A14B** | ~24-32 GB fp8 | **Take this on a 5090.** |

With 32 GB you can run the 14B at fp8 with block swap and generate at 1080p. If you hit OOM,
enable block swap / `--lowvram` before dropping to the 5B.

## 6. Verify the node

The template must contain a **`WanFirstLastFrameToVideo`** node with two image inputs. That node
is the entire point — it enforces your start and end frames as boundary conditions at t=0 and
t=1, so they are treated as ground truth while only the in-betweens are generated.

If your workflow has one image input, it is plain image-to-video and the building will drift.
Wrong workflow. Go back to step 4.

## 7. Output PNG, not video

In the save node, set the output to a **PNG image sequence**, not an MP4 or WebM. This is the
whole reason for running locally — do not undo it at the last step.
